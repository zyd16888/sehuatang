# 线路监测

更新爬虫代码 / 镜像并重启后，在管理页打开 **线路监测**。三个来源
`sehuatang`、`javbee`、`x1080x` 的公共会话池自动采样，无需修改现有配置。
页面按当前配置列出来源及代理，无需先启动采集。未检测、未采集的线路显示“暂无近期数据”。

## 代理重试与故障恢复

- 多代理时，网络失败（超时、DNS、连接、代理握手、TLS、发送和接收异常）立即退出当前线路的普通重试，
  释放 HTTP worker，再通过代理池选择其他可用线路重试同一 URL。
- 所有代理共用 `http.retry.attempts`，该值包含首次尝试；例如设为 3，即使配置 4 个代理也最多普通尝试 3 次。
  同线路 HTTP 503 等普通重试也消耗该额度；CF / R18 验证附加请求沿用原有统计与验证流程。
- 首次网络失败即隔离该代理访问该目标 origin 的路径，后续请求跳过该路径；其他目标 origin 不受影响。
  更早发出的成功响应不能解除较新的故障隔离。
- 隔离 60 秒后，在空闲 worker 上经原代理检测恢复；失败后再等待 60 秒，取得目标 HTTP 响应后解除网络隔离。
  403 / 429、CF / R18 验证仍按访问限制或验证状态展示，并沿用站点冷却与验证逻辑。
- 全部线路访问该目标均被隔离时，返回 `proxy_unavailable`，不伪装成 HTTP 429。失败沿用现有失败处理和检查点规则。
- 单代理或直连保留原线路内的普通重试，最终网络失败后同样隔离对应目标路径。
- 每个代理的 Session、Cookie / UA、验证锁和限速独立保留；已配置代理时不回退直连。

## 独立检测

管理页可点击 **检测全部**、筛选后的 **检测当前来源**，或卡片上的 **检测此线路**。
检测直接使用当前配置中的来源地址和代理，不创建抓取任务、不解析保存资源、不推进检查点。

检测先经原代理访问 `https://www.gstatic.com/generate_204`（预期 HTTP 204），再经同一代理访问来源首页。
代理端口不可连接时展示端口不可达；测试地址与目标站分别显示结果、耗时及最近检测时间。
检测使用来源配置 Cookie / UA，并遵守原限速；不自动启动 CF / R18 过盾。
繁忙或站点冷却中的线路等待空闲或冷却结束再执行，同线路重复提交会合并为一次检测。
检测成功仅说明响应可达，不代表采集、解析或保存已经成功。

## 统计口径

- 按来源、固定代理地址 / 端口和请求目标 origin（协议 / 域名 / 端口）隔离。
- 最近 5 分钟统计：HTTP 尝试次数、其中的普通退避重试次数、超时率、平均网络耗时，
  以及逻辑 HTTP 抓取的已完成 / 最终失败次数。一次超时后切换代理成功：两条线路合计
  2 次尝试、1 次重试、1 次完成、0 次最终失败；完成结果归于结束该请求的线路。
  失败数量不是解析、数据库保存或整轮采集的失败数。
- 网络耗时只计 HTTP Session 的实际请求，不包含排队、限速等待和退避睡眠。
- CF / R18 再验证请求按实际 HTTP 尝试采样；普通退避重试计数不包含验证流程的附加请求。
  Byparr / FlareSolverr 服务内部的浏览器请求不在此统计范围内。
- 诊断请求不计入采集尝试、最终失败和连续网络失败次数。
- 当前进程内保存统计，每条线路最多保留 16 个目标 origin，按秒聚合 5 分钟窗口；
  不写数据库。重启后重新采样；异常和网络响应恢复事件写入现有来源日志。
- 5 分钟没有真实采集请求或有效检测结果时显示“暂无近期数据”，不持续显示绿色；仍可查看最后成功时间
  和最近诊断时间。诊断成功只能证明可取得页面响应，不代表页面解析或保存已成功。

## 何时诊断

同一线路访问同一目标首次网络失败即隔离，连续 3 次网络失败后另标为“疑似异常”。网络失败包括
超时、DNS、连接、代理握手、TLS、发送和接收异常。403 / 429、CF / R18 验证及其他
异常 HTTP 响应单独展示，不直接推断代理断网。

诊断由公共会话池空闲 worker 执行：

1. 该线路没有在途工作、没有等待分配的采集请求，且目标至少 5 秒没有真实请求。
2. 故障隔离至少 60 秒后检测；同一来源内，同一线路所有目标合计最多每 60 秒启动一次自动诊断，同时最多一个。
3. 经原代理 GET 最近失败目标，复用该 worker 的 Session、Cookie / UA 与现有限速。
   单次请求超时为 `min(10 秒, 原请求 timeout)`；不执行过盾、不解析保存资源、不推进检查点。
4. 目标仍有网络错误时，连接代理服务端口（超时 3 秒）补充证据；端口可连后，经同一代理访问
   `https://www.gstatic.com/generate_204`（超时 10 秒、不跟随重定向），要求 HTTP 204。
   直连配置则直接测试该地址；已配置代理时绝不回退直连。
5. 已隔离路径持续低频检测，直到恢复或公共会话池关闭；健康但过期的线路由用户独立检测，不持续探测。

端口不可达提示检查代理服务 / 容器网络；测试地址可达而目标失败提示目标站访问路径异常。
测试地址也失败时仅显示“暂无法判断”，不自动认定节点失效。代理端口可连接不等于代理握手成功。
单轮诊断最多包含目标请求、端口连接与一次测试请求，限速等待另计。

较早发出的请求晚到，以及诊断期间出现更新的真实请求结果，都不能误清除更新的异常证据。
停止公共会话池会停止诊断调度，已有网络调用按请求超时收尾。

## 日志与 API

现有重试告警和新增最终失败告警包含脱敏代理地址、单次 `elapsed_ms`、`curl_code`、
`phase` 和固定安全摘要。curl 28 只能确定超时，`phase=unknown`，不猜测连接 / 读取阶段。
不输出底层异常原文到新增诊断日志或 API，避免代理用户信息泄露。

`GET /api/network` 使用与 `/api/status` 相同的鉴权，返回 `window_seconds` 与 `lines`。
GET 接口按配置建立或复用公共会话池，不发起网络探测，不返回 Cookie、代理账号密码或完整目标 URL 的查询参数。
`POST /api/network/check` 使用相同鉴权；JSON 可传 `source` 和整数 `proxy_slot`，省略来源检测全部，
只传来源检测该来源全部线路，同时传代理编号检测单条。响应 `queued` 为新排队的线路数量。
目标 URL 固定来自来源配置，客户端不能通过该接口指定任意探测地址。
管理页每 5 秒随已有轮询刷新，支持按来源筛选、空状态、失败状态和过期状态。

故障转移只在已配置代理端口间分配 HTTP 请求，不操作代理管理器的节点或出口 IP。
原有站点限流保护继续生效；诊断遇到站点限流时也遵循原冷却规则。
